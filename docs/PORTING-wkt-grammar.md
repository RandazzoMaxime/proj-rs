# Porting: the WKT grammar checks of `createFromWKT`

PROJ 9.9.0 checks a WKT text against a formal grammar after it builds the object from it
(`WKTParser::createFromWKT`, `src/iso19111/io.cpp:8508-8522`). The dialect comes from
`guessDialect`: WKT1 GDAL and WKT1 ESRI go through `pj_wkt1_parse`, WKT2 2015 and 2019 through
`pj_wkt2_parse`. A non-empty message goes to `emitGrammarError` (io.cpp:1544-1550): strict mode
throws it, lax mode appends it to `grammarErrorList`. A text that does not build never reaches the
check, so its only error is the builder's.

proj-rs does the same in `WktParser::create_from_wkt` (`src/iso19111/wkt_import.rs`), after
`build_from_wkt`, with the dialect of its `guess_dialect`. The grammar error is the last entry of
`grammar_errors()`, after the ones the builder emitted (`not required number of children in
SPHEROID node`), as in PROJ.

## The grammars

`src/wkt1_grammar.y` and `src/wkt2_grammar.y` are bison grammars with no semantic actions and no
`error` rule. `src/wkt1_generated_parser.c` and `src/wkt2_generated_parser.c` are their LALR
parsers, generated by GNU Bison 3.5.1 with the `yacc.c` skeleton and `%define parse.error
verbose`. proj-rs does not run bison: it uses the tables of those generated files.

- `tools/wkt-grammar/extract.py <PROJ source dir>` reads the two `.c` files, the token enums of
  `wkt{1,2}_generated_parser.h` and the `tokens[]` tables of `wkt{1,2}_parser.cpp`, and writes
  `src/iso19111/wkt_grammar/wkt1_tables.rs` and `wkt2_tables.rs`: `YYFINAL`, `YYLAST`,
  `YYNTOKENS`, `YYPACT_NINF`, `YYMAXUTOK`, `YYUNDEFTOK`, `yytranslate`, `yytname` (terminals),
  `yypact`, `yydefact`, `yypgoto`, `yydefgoto`, `yytable`, `yycheck`, `yyr1`, `yyr2`, the token
  values the lexers return, and the lexer keyword list in its order. It refuses a parser that is
  not bison 3.5.1 `yacc.c`, or whose `yytable_value_is_error` is not `0` (the driver assumes
  it; `YYTABLE_NINF` is then never read and is only recorded in the header comment).
- The generated files are committed. Run the script again on a new PROJ version; its output is
  stable under `cargo fmt`.

## The driver (`src/iso19111/wkt_grammar/mod.rs`)

`yyparse` follows the `yacc.c` loop: `yysetstate` (stack depth check against `YYMAXDEPTH`, 10,000,
with the `memory exhausted` message; accept on `YYFINAL`), `yybackup` (default action when
`yypact` is `YYPACT_NINF`, else read a token; a lexer value of 0 or less is the end of input),
shift, `yydefault`, `yyreduce` (pop `yyr2`, goto by `yypgoto` / `yydefgoto`), `yyerrlab` and
`yyerrlab1`. The grammars have no `error` rule, so recovery pops the whole stack and aborts after
the first message; the loop is still the skeleton's, table for table.

`yysyntax_error` is ported with `YYERROR_VERBOSE_ARGS_MAXIMUM = 5`: the unexpected token, then up
to four expected tokens of the state (`syntax error, unexpected %s, expecting %s or %s ...`). A
fifth expected token drops the whole list (`syntax error, unexpected ','`). With no lookahead the
message is `syntax error`. `yytnamerr` strips the double quotes of `"PARAMETER"` unless the name
holds an apostrophe, a comma, or a backslash that does not escape a backslash.

`pj_wkt_error` (`src/wkt_parser.cpp`) builds `Parsing error : <msg>. Error occurred around:\n`,
the input bytes from 40 before to 40 after `pszLastSuccess` (the start of the last token read),
cut at line breaks, a newline, spaces up to that position, and `^`.

## The lexers

- `wkt1.rs` is `pj_wkt1_lex` (`src/wkt1_parser.cpp:94-193`): whitespace, keywords
  (`ci_starts_with`, then the next byte must not be a letter), double-quoted strings without
  escapes, signed numbers with fraction and exponent, letter-only identifiers, else one byte.
- `wkt2.rs` is `pj_wkt2_lex` (`src/wkt2_parser.cpp:243-336`): keywords, unsigned integers (`1`,
  `2`, `3` alone are their own character tokens), double-quoted strings with `""` escapes, the
  printed quotes U+201C ... U+201D of OGC 12-063r5, else one byte.
- An unterminated string is the end of input. A byte from 0x80 outside a string is a negative C
  `char`, which bison reads as the end of input.
- The input is the UTF-8 bytes of the text, up to the first NUL (`wkt.c_str()`); positions are
  byte offsets.

## Bytes, not characters

The 40-byte window of `pj_wkt_error` can start or end inside a UTF-8 sequence, and PROJ keeps the
cut bytes. Every place that PROJ writes such a message writes those bytes:

| Where | proj-rs |
|---|---|
| `out_grammar_errors` of `proj_create_from_wkt`, lax | `WktParser::grammar_error_bytes()`, listed by the C API |
| the same, `STRICT=YES` | `WktParser::failure_bytes()`, listed by the C API |
| the log line when no list is asked | the same bytes, through `Ctx::fail_bytes` |
| the `Grammar error:` lines of `projinfo` | `Report::warning_bytes`, which the binary writes to stderr |

`grammar_errors()`, the `FactoryError` text and `Report::warnings` are the `String` forms, where
an incomplete sequence reads U+FFFD. The callback of `run_with_callback` receives that `String`
form too, as its type is `&str`.

## What the check found

The `DERIVEDPROJCRS` export wrote the CS of a 3D geodetic base inside `BASEPROJCRS.BASEGEOGCRS`,
and the cartesian CS of a 3D `BASEPROJCRS`. PROJ writes neither (crs.cpp:6874-6955), and its WKT2
grammar refuses the first, so the strict round trip of `tests/unit_crs_core_2.rs`
(`crs_promote_to_3d_and_demote_to_2d`) failed. The export now follows PROJ, and the import
promotes a 2D base of a 3D `DERIVEDPROJCRS` as `buildDerivedProjectedCRS` does
(io.cpp:5668-5672).

## Verification

- `tests/wkt_grammar.rs`: WKT1 and WKT2, unexpected token, 1 to 4 expected tokens, more than 4,
  end of input, printed quotes, `""`, context window across line breaks, the cut UTF-8
  sequence, strict mode. Expected texts from the reference libproj (`proj_create_from_wkt`
  through `capi/tests/wkt_warnings.c`, and `projinfo` for multi-line texts).
- `tests/test_wkt1_syntax.rs`: the WKT1 cases of `projinfo`.
- `tests/wkt_grammar_bytes.rs`: a strict failure and the `projinfo` line that cut a character,
  with the bytes of PROJ 9.9.0 (`tests/data/utf8_cut`).
- `capi/tests/run.sh wkt_warnings`: the EPSG export, warnings and grammar errors identical to
  libproj; then about 69,000 malformed texts generated from it, whose grammar errors must match
  libproj wherever the object and the other messages match (`capi/tests/grammar_errors.py`);
  then the 19 texts of `capi/tests/wkt_utf8.txt`, with accented names and seven whose context
  cuts a character, in lax and in strict mode (`wkt_warnings strict`).
  Texts where the builder already differs (a different refusal message, a missing or extra
  warning on malformed input) are counted apart: they are builder gaps, not grammar ones.
